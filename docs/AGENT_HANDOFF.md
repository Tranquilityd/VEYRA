# Agent Handoff

## PROJECT: Veyra

Repository/product branding is **VEYRA / VEYRAWLD**. This handoff describes the preserved implementation at migration time.

## CURRENT STATUS

Veyra is a working native-JavaScript Canvas game with a city/garden world, Lester player character, NPCs/animals, casino and arcade interiors, browser-wallet authentication, server-backed balances/rewards, manual Arcade withdrawals, and an existing LitVM casino contract integration.

The current source passes `npm run check`, all 121 regular tests, and `npm run build:static` as of 4 October 2026. Build output is generated into ignored `static-site/`. Production configuration/secrets are external and are not part of Git.

The known unresolved user-facing issue is a reported Production wallet connection failure occurring before the backend receives an auth challenge request. Existing evidence points to browser/provider injection, permission, chain switching, or account request behavior; it has not been reproduced in a wallet-enabled browser in this workspace. Do not guess or rewrite the wallet system without exact browser evidence.

## IMPORTANT RULE

**Do not rewrite working systems unnecessarily.** Preserve function, visuals, gameplay, Lester, the garden/city, animation timing, camera, controls, economy, wallet security, fairness, branding, and architecture. Reproduce and verify a bug before changing code. Use the smallest safe change and regression tests.

## CURRENT ARCHITECTURE

### Client

`index.html` loads CSS and `src/main.js` as a browser ES module. `main.js` installs the LitVM wallet adapter, creates `Game`, and boots it. `Game` composes core systems, event bus, state machine, game registry, UI, world, and integrations. Rendering is custom Canvas 2D plus DOM/CSS overlays; there is no React/Vue framework.

### Game/runtime

- `src/core/`: main loop, input, state, audio, storage/save, movement, quality guard.
- `src/states/`: Boot, Menu, outdoor Play, Interior, and world rendering.
- `src/world/`: camera, world/entity management, city map/atlas, venue/interior definitions.
- `src/entities/`: Lester/player, rig/animator, NPCs, animals, vehicles, buildings, venue and machine entities.
- `src/visuals/`: code-painted characters, city, props, casino, arcade, lighting, palette, sprites.
- `src/systems/`: interactions, conversations, transitions, world entry, venue floors, games, wallet/session, referral.
- `src/ui/`: overlay, wallet, balances, minimap, CAPTCHA, orientation, and arcade game UI.
- `src/games/`: casino/arcade rules, wagering, rewards, and provably-fair verification.

### Backend

Vercel routes in `api/` delegate to modules in `server/`. PostgreSQL persistence uses `db/schema.sql`. Server modules enforce wallet authentication, CAPTCHA verification, receipt/event verification, deterministic casino resolution, signed claims, server-authoritative Arcade rounds, withdrawals, referrals/social verification, audit records, and admin workflows.

### Build/deployment

`scripts/build-static.js` recreates `static-site/` from browser source and injects only public CAPTCHA settings. `vercel.json` defines this build/output and serverless routes. `static-site/`, `node_modules/`, `.vercel/`, local env files, contract artifacts, caches, and test results must not be committed.

### Blockchain

- LitVM LiteForge chain 4441 (`0x1159`), native zkLTC.
- Existing VeyraCasino: `0xd2c36B83B1Ca788743E3E9b339e043b6B04e3273`.
- Manifest: `config/deployments/liteforge.json`; ABI: `config/abi/VeyraCasino.json`.
- Contract source: `contracts/contracts/VeyraCasino.sol`.
- Wager is a payable native-token transaction. Backend independently verifies its receipt/event and on-chain session.
- Winning outcome receives an EIP-712 backend authorization; user submits `claimWinnings` on-chain.
- Replay/deadline/session/wager/liquidity guards exist. Outcomes are off-chain deterministic, not generated by the contract.
- Do not redeploy or change chain/signer/treasury configuration without explicit approval.

## KNOWN ISSUES

1. Wallet connection report stops before `/api/auth/challenge`; exact wallet/browser error is still unavailable.
2. LiteForge public RPC can time out on broad historical log ranges.
3. Explorer values/indexing can lag direct RPC state; deployed contract source is not explorer-verified.
4. Current contract has no arbitrary treasury withdrawal/recovery path.
5. Signer availability and treasury liquidity are required for winning claims.
6. Multi-stage wager/backend/claim reconciliation can be confusing after network interruption.
7. Full app behavior needs external env vars, PostgreSQL, CAPTCHA, wallet provider, and serverless routing; static hosting alone is incomplete.
8. `.env.local` contains real local/deployment-sensitive values and must remain excluded. Never print or copy them.

## DEVELOPMENT RULES

- Never expose private keys, CAPTCHA secrets, session secrets, database credentials, signatures, cookies, or auth tokens.
- Never commit `.env.local`, `.vercel/`, `node_modules/`, generated `static-site/`, contract artifacts/cache, or test outputs.
- Do not initialize or rewrite Git history as incidental project work. The repository owner controls GitHub setup.
- Do not change Production, environment variables, database records, aliases, CAPTCHA provider, LitVM config, or deployed contract without approval.
- Do not run destructive database operations or E2E tests against Production. Use isolated local/test databases.
- Do not redeploy the existing contract merely to test or migrate source.
- Do not alter Lester, garden/city, UI, art style, animations, controls, camera, gameplay, multipliers, timing, or economy unless explicitly requested.
- Do not trust client-provided game, score, wave, reward, payout, or result data.
- Keep financial arithmetic in integer atomic units.
- Arcade financial rewards must derive only from server-verifiable progression. Disable financial rewards when verification is infeasible.
- Keep Arcade withdrawals manual; deduct only at the established final admin sent/paid transition.
- Preserve existing fairness versions and historical verification.
- Passing tests do not by themselves establish release readiness. Verify behavior and operational configuration separately.
- Before changes: inspect relevant files and tests, reproduce the issue, establish a baseline, make the smallest change, add regression coverage, rerun checks/build.
